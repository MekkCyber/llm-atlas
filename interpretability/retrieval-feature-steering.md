# Retrieval Feature Steering (Xetrieval)

*Depth — applying SAE-style sparse feature decomposition to dense retrieval embeddings, with per-feature natural-language labels and intervention-based steering.*

**TL;DR:** Dense retrievers score via opaque dot products on high-dim embeddings; existing explanations stop at token alignments. Xetrieval (1) injects CoT-style reasoning directly into the embedding via a lightweight "reasoning internalizer" (single forward pass, no autoregressive generation), then (2) decomposes the enriched embedding with an SAE-style sparse decoder. Each surviving feature gets a coherent natural-language label. Document-query similarity is rewritten as the *overlap* of named features — supporting both inspection and task-level steering.

## What it is

A mechanistic-interpretability framework for dense retrievers — the first to bring SAE-style feature decomposition to retrieval embeddings, which previously had no analogous interp toolkit.

## How it works

Two-stage pipeline applied on top of a frozen dense retriever:

1. **Reasoning internalizer.** A small projector takes the retriever's sentence embedding and emits an *enriched* embedding that contains CoT-style reasoning information — without ever running autoregressive generation. The projector is trained to match the embedding of a (sentence + generated reasoning) sequence to that of (sentence alone passed through the projector). Inference is one forward pass.
2. **Sparse decoder.** A wide sparse autoencoder is trained on the enriched embeddings. Each surviving feature is labeled by inspection of its top-activating sentences (the same recipe as LLM SAEs — see [sae.md](sae.md)).

At retrieval time, a query embedding and a document embedding are each decomposed into their sparse-feature activations. The retrieval score factors as a function of *which features overlap*, not just a dot product magnitude. The activated features for both query and document are human-readable, so the explanation is "this document matches because it shares the {causal-mechanism, evaluation-protocol, dataset-size} features with the query."

**Steering.** Knock features in or out at the document-side or query-side encoder and observe what changes. The paper reports task-level feature steering: amplify a "novelty" feature on the query side and the retriever's results shift toward novel-claim documents.

## Why it matters

- First mechanistic-interp paradigm for dense retrieval. Earlier work stopped at token-level salience (BM25-style alignments) or post-hoc text rationales generated by an LLM — neither of which inspects the actual retrieval mechanism.
- The "reasoning internalizer" sidesteps the latency cost of CoT for retrieval. Most "reason-then-retrieve" pipelines need an LLM forward pass per query; this gets the same enrichment in one cheap forward.
- Steering enables retrieval *editing* without retraining the retriever — useful for debiasing, novelty tuning, or domain adaptation at deployment.

## Gotchas & tricks

- The SAE quality determines explanation quality. Use top-$k$ variants and feature-splitting checks (see [sae.md](sae.md)) before claiming any feature is monosemantic.
- The reasoning internalizer is trained on (sentence, reasoning) pairs; the quality of the reasoning training data caps the quality of the enrichment. Domain-mismatched reasoning data degrades the projector.
- Steering effects vary by feature. Some directions shift retrieval cleanly; others produce noise. Sanity-check each steerable feature on a held-out query set before deploying.
- Per-feature explanations are post-hoc labels. They are *evidence* for what a feature does, not proof — humans can over-interpret top-activating examples.
